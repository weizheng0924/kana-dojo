# 50音學習 App 設計文件

- 日期:2026-10-20
- 形式:純前端靜態網頁(PWA),部署於 GitHub Pages
- 狀態:已與使用者確認設計,進入實作規劃階段

## 1. 目標與範圍

做一個手機也能用的網頁 App,幫助使用者認識日文 50 音(平假名 + 片假名,含濁音/半濁音/拗音),透過「每日固定題數測驗」養成習慣,自動記錄每個假名的答對/答錯狀況,並讓使用者能回顧、加強答錯的假名。

不做的事(YAGNI,明確排除於本次範圍):
- 不做帳號系統、不做雲端同步、不做後端伺服器
- 不做單字/句子學習,只做 50 音本身
- 不做輸入羅馬拼音打字題型,只做選擇題
- 不做離線語音檔,發音完全依賴瀏覽器內建 TTS(Web Speech API),若裝置不支援則隱藏發音按鈕

## 2. 內容分級與解鎖

將 50 音分成六個階段(tier),依序解鎖:

| Tier | 內容 | 字數(約) |
|------|------|----------|
| 1 | 平假名清音(あ〜ん) | 46 |
| 2 | 平假名濁音・半濁音(が〜ぽ) | 25 |
| 3 | 平假名拗音(きゃ〜ぴょ) | 36 |
| 4 | 片假名清音 | 46 |
| 5 | 片假名濁音・半濁音 | 25 |
| 6 | 片假名拗音 | 36 |

**解鎖條件**:目前 tier 內「每個假名至少被測過 3 次」且「該 tier 整體正確率 ≥ 80%」時,自動解鎖下一 tier。未解鎖的 tier 不會出現在測驗題庫或 50 音總覽表中(以鎖頭圖示表示)。

## 3. 每日任務

- 每日固定 15 題,題庫為「目前已解鎖的所有假名」
- 出題採**加權隨機抽樣**:每個假名的被抽中權重 = `1 + wrongRate * K`(wrongRate = 該假名歷史答錯率,K 為放大係數,預設 3),確保答錯多的假名更常出現,同時保證新手假名(seen=0)有基礎權重不會被冷落
- 同一回合盡量不重複抽同一假名(題庫 ≥ 15 時不重複;題庫不足 15 時允許重複抽)
- 全部 15 題作答完畢即視為當日任務完成,不可中途放棄後重算(中斷重進可從上次進度繼續,直到裝置時間換日才重置)

**題型**:畫面顯示一個假名(大字),下方 4 個羅馬拼音選項,其中 1 個正確、3 個干擾選項(優先從同 tier 內容取相似音干擾,例如 し vs ち vs じ,增加鑑別度)。點擊假名圖示可播放 TTS 發音。選完立即顯示對/錯,錯誤時高亮正確答案,約 0.8 秒後自動跳下一題。

## 4. Streak(連續天數)與日期判定

- 以裝置「當地日曆日期」(`YYYY-MM-DD`,依瀏覽器 `Date` 取本地時區)為一天的單位
- 完成當日任務時:若 `lastCompletedDate === 昨天` → streak +1;若 `lastCompletedDate === 今天`(已完成過)→ 不重複累加;否則(間隔超過一天)→ streak 重置為 1
- App 開啟時若發現「今天」尚未完成且昨天也沒完成,只在畫面上顯示目前 streak 已中斷(歸零),不做特殊彈窗提醒(避免過度打擾,保持簡潔)

## 5. 錯題本與複習

獨立頁面,列出所有「已經測過至少一次」的假名,預設依「最近答錯時間新到舊」排序,可切換依「答錯率高到低」排序。每筆顯示:假名、羅馬拼音、答對/答錯次數、正確率、發音按鈕。

頁面底部提供「只練錯題」按鈕:從錯題本中正確率 < 80% 的假名抽題,開啟一個獨立的練習回合(題數視錯題數量動態決定,最多 15 題)。這個練習**不計入每日任務進度、不影響 streak**,純粹讓使用者自由加強,但作答結果仍會更新該假名的統計數字(因此也會間接影響之後每日任務的出題權重與 tier 解鎖判斷)。

## 6. 首頁(Dashboard)

- 頂部:今日任務進度(例:8/15)、目前 streak 天數與最長紀錄
- 中段:50 音總覽表格,依 tier 分區塊顯示,每個假名格子依狀態上色:
  - 灰色:尚未解鎖
  - 黃色:已解鎖但正確率 < 80%
  - 綠色:已解鎖且正確率 ≥ 80%
  - 點擊任一格子可看該假名的詳細數字(答對/答錯次數、正確率)小彈窗,並可播放發音
- 底部兩個主要入口:「開始今日任務」大按鈕(若今日已完成則顯示「今日已完成 ✓,明天再來」並仍可重新瀏覽但不加分)、「錯題本」次要按鈕

## 7. 資料模型(localStorage)

```json
{
  "version": 1,
  "unlockedTier": 0,
  "kana": {
    "あ": { "seen": 12, "correct": 10, "wrong": 2, "lastWrongAt": 1763600000000 }
  },
  "dailyTask": {
    "date": "2026-10-20",
    "questionIds": ["あ", "か", "..."],
    "answeredCount": 8,
    "correctCount": 6,
    "completed": false
  },
  "streak": {
    "current": 5,
    "longest": 12,
    "lastCompletedDate": "2026-10-19"
  },
  "settings": {
    "ttsEnabled": true
  }
}
```

- 讀寫集中在單一模組 `js/storage.js`,其他模組一律透過它存取,不直接碰 `localStorage`
- 啟動時偵測 `localStorage` 是否可用(try/catch 寫入測試值),不可用時切換為記憶體內的物件模擬,並在畫面頂部顯示一條不可關閉但不擋互動的提示橫幅:「目前瀏覽模式無法保存進度,離開後資料將遺失」

## 8. 檔案結構與技術選型

純 Vanilla HTML/CSS/JavaScript,不使用任何框架或建構工具,降低部署與維護成本,完全符合「靜態網頁丟 GitHub Pages」的需求。

```
/
├─ index.html
├─ styles.css
├─ manifest.json        # PWA manifest,可加到主畫面
├─ sw.js                # Service Worker,快取靜態資源供離線使用
├─ icons/
│  ├─ icon-192.png
│  └─ icon-512.png
├─ data/
│  └─ kana.js           # 50音資料表 + 六個 tier 定義 + 干擾選項分組
├─ js/
│  ├─ storage.js        # localStorage 讀寫 + fallback
│  ├─ quiz.js           # 出題/加權抽樣演算法(純函式,不碰 DOM)
│  ├─ unlock.js         # tier 解鎖判斷(純函式)
│  ├─ streak.js         # streak 計算(純函式)
│  ├─ tts.js            # Web Speech API 封裝,含不支援時的降級處理
│  ├─ router.js         # 簡單 hash-based 畫面切換
│  └─ views/
│     ├─ dashboard.js
│     ├─ quiz.js
│     ├─ result.js
│     └─ review.js
└─ docs/superpowers/specs/
   └─ 2026-10-20-kana-learning-app-design.md
```

純邏輯模組(`quiz.js`、`unlock.js`、`streak.js`)刻意寫成不依賴 DOM、不依賴全域狀態的獨立函式(輸入資料 → 輸出結果),方便用 Node.js 內建 `assert` 寫輕量測試腳本(`test/*.test.mjs`,用 `node --test` 執行),不需要安裝任何測試框架。

## 9. 視覺與品質要求(使用者特別要求「不要讓人笑話」)

- Mobile-first 響應式設計,主要在手機瀏覽器直向畫面下測試(也要能在桌面瀏覽器正常顯示,寬度自動調整,不能跑版)
- 乾淨現代的視覺風格:清楚的字體大小(假名主顯示字至少 64px 起跳)、足夠的點擊區域(≥44px,符合行動裝置觸控標準)、合理的留白與配色對比(符合基本無障礙對比度)
- 提供正式的 PWA icon(192px / 512px)與 `manifest.json`(含 `name`、`short_name`、`theme_color`、`background_color`),讓「加入主畫面」後有正常的 App 圖示與啟動畫面,不是預設破圖
- 網頁 `<title>` 與 favicon 要設好,不留瀏覽器分頁顯示「Untitled」或空白圖示的狀況
- 無 console error/warning(含 Service Worker 註冊失敗等),基本防呆:陣列為空、localStorage 損毀(JSON.parse 失敗)時要能優雅重置而不是整頁白屏
- 發音功能在不支援 `speechSynthesis` 的瀏覽器(例如部分舊版 iOS Safari 或特殊瀏覽器)要自動隱藏發音按鈕,不能讓使用者點了沒反應或丟出錯誤

## 10. 部署

- 直接將整個資料夾 commit 進 GitHub repo,於 repo 設定開啟 GitHub Pages(可選擇從 `main` branch 根目錄,或之後視需要改放 `/docs`)
- 不需要 CI/build 流程;若之後想自動化,可另外加一個單純檢查(例如跑 `node --test`)的 GitHub Actions,但不在本次範圍內
